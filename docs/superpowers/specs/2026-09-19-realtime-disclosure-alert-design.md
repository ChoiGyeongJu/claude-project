# 실시간 공시·시장 이벤트 알림 서비스 — 설계

- 작성일: 2026-09-19
- 상태: 초안 (리뷰 대기)
- 레포: https://github.com/ChoiGyeongJu/claude-project

## 1. 개요

주식·코인 시장에 영향을 주는 공시와 뉴스를 **최대한 실시간으로** 선별·요약해 메신저로 전달하는 서비스.

1단계는 국내 전자공시(DART)를 대상으로 하는 **텔레그램 알림 봇**이다. 화면이 없는 상주 워커 프로세스이며, 웹 대시보드는 2단계에서 별도 배포 단위로 추가한다.

### 목표

- 장중 기준 **2~3초 폴링**으로 주가 영향이 큰 공시를 선별 발송
- 운영자가 **3일간 코드를 보지 않아도** 스스로 굴러가는 파이프라인
- 소스(공시/코인/뉴스)를 **플러그인으로 추가**할 수 있는 구조
- 월 고정비 **$10 이하**

### 비목표 (명시적으로 하지 않는 것)

- **투자 판단 제공 금지** — 호재/악재 판정, 목표가, 매수·매도 의견을 생성하지 않는다. 유사투자자문 규제 회피를 위한 설계 제약이며 타협하지 않는다.
- 밀리초 단위 속도 경쟁 — API가 폴링 전용이라 구조적으로 불가능하다.
- 매매 자동화·주문 연동
- 1단계에서의 웹 UI

| 실시간 장애 대응 | **불가** | 자가치유 4계층 + 외부 감시 필수 |

## 3. 범위와 단계

| 단계 | 소스 | 산출물 | 비고 |
|---|---|---|---|
| **1** | DART 공시 | 워커 + 텔레그램 채널 | 본 스펙의 대상 |
| 2 | 코인 거래소 공지 | 소스 어댑터 추가 | 24/7. 공지 API 비공개라 ToS 검토 선행 |
| 3 | 뉴스 | 소스 어댑터 추가 | 저작권 제약 (제목+링크+자체 요약만) |
| W | — | Next.js 웹 대시보드 | 소스 단계와 독립. 1단계 안정화 후 착수 |

1단계에서 만든 중복제거·발송·재시도·감시 인프라를 2·3단계가 그대로 재사용한다. 소스 추가 시 변경 범위는 **어댑터 1개 + 룰셋 1개**로 한정된다.

## 4. 아키텍처

### 4.1 형태

프레임워크 없는 **Node.js 상주 프로세스**. HTTP 서버를 띄우지 않는다 (모든 I/O가 아웃바운드). Docker 컨테이너로 패키징해 OCI VM에서 구동한다.

```
while (true) {
  const events = await poll()
  await process(events)   // 정규화 → 중복제거 → 필터 → 요약 → 발송예약
  await heartbeat()
  await sleep(interval)
}
```

### 4.2 패턴

**Hexagonal (Ports & Adapters)** + **Pipes & Filters**.

핵심 규칙 하나: **도메인 코어는 순수 함수다. 네트워크도 DB도 만지지 않는다.**

제품의 본체인 필터가 순수 함수여야 네트워크 없이 검증 가능하다. 이 규칙이 깨지면 골든 테스트셋 전략이 무너진다.

### 4.3 데이터 흐름

```
Poller ──2.5s──▶ OpenDART API
  │ RawEvent[]
  ▼
Normalize ──▶ Dedup (rcept_no UNIQUE) ──▶ 1차 룰 필터 (0ms, $0)
                                              │ pass
                                              ▼
                                    2차 LLM (high/normal만)
                                              │
                                              ▼
                                    Outbox ──▶ Telegram
Heartbeat ──▶ 외부 감시 서비스
```

### 4.4 레포 구조

```
claude-project/
├── apps/
│   ├── worker/          # 1단계 · Node 데몬
│   └── web/             # 2단계 · Next.js
├── packages/
│   ├── db/              # Drizzle 스키마 (worker/web 공유)
│   └── shared/          # worker·web 공유 타입 (워커 내부 core/ 와 구분)
├── docs/superpowers/specs/
└── package.json         # pnpm workspace
```

모노레포 근거: 워커가 쓴 데이터를 웹이 읽으므로 **스키마와 타입이 단일 출처**여야 한다.

### 4.5 워커 내부 구조

```
apps/worker/src/
├── core/                   # 순수 · 외부 의존 0
│   ├── event.ts            #   NormalizedEvent
│   ├── filters/dart-rules.ts   #   (Event) => Verdict  ← 제품의 본체
│   └── policy.ts           #   발송 정책 (TTL, 지연 상한)
├── ports/                  # 인터페이스만
│   ├── source.ts  store.ts  notifier.ts  summarizer.ts
├── adapters/               # 교체 가능한 외부 연동
│   ├── sources/dart.ts
│   ├── store/postgres.ts
│   ├── notifier/telegram.ts
│   └── summarizer/llm.ts
├── pipeline/run.ts
└── main.ts                 # 진입점 · 의존성 주입
```

의존성 방향은 단방향이다. **`apps/worker/src/core/`는 아무것도 import하지 않는다.**
(`packages/shared/`는 worker·web이 공유하는 타입 전용이며, 워커 내부의 `core/`와는 다른 것이다.)

### 4.6 핵심 타입

```ts
type NormalizedEvent = {
  sourceId: string       // "dart" | "upbit" | ...
  externalId: string     // 소스 고유 ID → 멱등키
  occurredAt: Date
  firstSeenAt: Date
  title: string
  url: string
  subject?: { name: string; ticker?: string; market?: string }
  raw: unknown
}

type Verdict =
  | { action: 'drop'; reason: string }
  | { action: 'pass'; tier: Tier; rule: string }

type Tier = 'critical' | 'high' | 'normal'
```

## 5. 데이터 모델

```sql
CREATE TABLE events (
  id            bigserial PRIMARY KEY,
  source_id     text        NOT NULL,
  external_id   text        NOT NULL,   -- DART: rcept_no (14자리)
  occurred_at   timestamptz,
  first_seen_at timestamptz NOT NULL,
  title         text        NOT NULL,
  url           text        NOT NULL,
  corp_name     text,
  ticker        text,
  market        text,                   -- Y | K
  verdict       text        NOT NULL,   -- pass | drop
  tier          text,                   -- critical | high | normal | NULL
  rule          text        NOT NULL,   -- 매칭 룰명 또는 drop 사유
  raw           jsonb       NOT NULL,
  UNIQUE (source_id, external_id)
);

CREATE TABLE outbox (
  id              bigserial PRIMARY KEY,
  event_id        bigint      NOT NULL REFERENCES events(id),
  payload         jsonb       NOT NULL,
  status          text        NOT NULL,  -- pending | sent | dead
  attempts        int         NOT NULL DEFAULT 0,
  next_attempt_at timestamptz NOT NULL,
  expires_at      timestamptz NOT NULL,  -- 티어별 TTL
  last_error      text
);

CREATE TABLE api_usage (
  usage_date date NOT NULL,              -- KST 기준
  source_id  text NOT NULL,
  call_count int  NOT NULL DEFAULT 0,
  PRIMARY KEY (usage_date, source_id)
);
```

`drop`된 이벤트도 **반드시 사유와 함께 기록**한다. 기록이 없으면 과필터링을 발견할 수단이 사라진다.

## 6. 수집

### 6.1 API

- 엔드포인트: `https://opendart.fss.or.kr/api/list.json`
- 파라미터: `page_count=100`, `sort=date`, `sort_mth=desc`
- 주기당 호출 **1회**. 2~3초 사이에 100건 이상 접수되는 경우는 없다.

### 6.2 한도와 폴링 주기

공식 한도는 **일 20,000건**이다 (에러코드 `020` 설명 기준). 문서 조사 단계에서 인용했던 "일 1만 건"은 오류였다.

| 구간 | 주기 | 근거 |
|---|---|---|
| 평일 08:00–19:00 | **2.5초** | 공시 접수 집중 |
| 평일 그 외 | 30초 | 산발적 |
| 주말·공휴일 | 5분 | 거의 없음 |

`api_usage`로 일일 호출을 추적하고 **자정(KST)에 리셋**한다. 잔여 예산이 임계 이하면 주기를 자동 확대한다. **한도 초과로 서비스가 멈추는 것이 최악의 실패**이므로 보수적으로 운용한다.

### 6.3 중복 방지

`rcept_no`(접수번호 14자리)는 공시마다 유일하므로 그대로 멱등키로 쓴다. `UNIQUE (source_id, external_id)` 제약이 중복 발송을 **구조적으로** 차단한다. 애플리케이션 로직으로 판단하지 않는다 (경쟁 조건 취약).

### 6.4 재시작 복구

이미 본 공시는 `rcept_no` 기반으로 걸러 DB 에 닿지 않게 한다. 목록 API 는 날짜 창을 주지 않으면 같은 최신 100건을 매 폴링마다 돌려주므로, 이를 거르지 않으면 2.5초마다 100건을 각각 트랜잭션으로 쓰게 되어 **목표 주기 자체가 달성 불가능해진다**. 유니크 제약은 그래도 최후의 정합성 보루로 남는다.

**재기동 직후 첫 사이클은 기록만 하고 발송하지 않는다.** 장시간 다운 후 밀린 공시가 한꺼번에 쏟아지는 것을 막는다.

> 설계 변경 이력: 최초 스펙은 "접수 후 10분이 지나면 발송하지 않는다"였으나 **구현이 불가능했다.** DART 목록 API 는 접수 *시각* 을 주지 않고 날짜(`rcept_dt`)만 주므로, 워커는 "우리가 그 공시를 처음 본 시각"밖에 알 수 없고 그 값은 정의상 항상 `now` 다 — 경과 시간이 영원히 0 이라 게이트가 발동하지 않는다. 최종 리뷰에서 죽은 코드임이 드러나 **재기동 직후 억제**로 대체했다. 이쪽이 원래 의도(재기동 폭탄 방지)를 실제로 달성한다.

## 7. 필터

### 7.1 티어 — 속도가 처리 경로를 결정한다

| 티어 | 처리 | 지연 | 예시 |
|---|---|---|---|
| `critical` | **LLM 생략, 즉시 발송** (요약은 후속 보강) | ~0.3초 | 공급계약, 무상증자, 횡령·배임, 상장폐지 |
| `high` | 본문 조회 → LLM 요약 → 발송 | ~3초 | 손익구조 30% 변동, 타법인 취득 |
| `normal` | 동일, 낮은 우선순위 | ~3초 | 배당결정 등 |

제목만으로 정보가 충분한 공시에 LLM 지연을 붙이면 2.5초 폴링이 무의미해진다.

### 7.2 1차 룰 필터 (순수 함수, 0ms, $0)

순차 게이트:

| # | 조건 | 판정 | 근거 |
|---|---|---|---|
| 1 | `stock_code` 없음 | drop | 비상장 — 주가 없음 |
| 2 | `corp_cls` ∉ {Y, K} | drop | 코넥스·기타 제외 (거래량 미미) |
| 3 | `report_nm`이 정기보고서 패턴 | drop | 사업/반기/분기보고서 — 예정된 일정 |
| 4 | `report_nm` 접두어 | 분기 | 아래 표 |
| 5 | `report_nm` 노이즈 패턴 | drop | 아래 목록 |
| 6 | `report_nm` 키워드 매칭 | tier 부여 | 아래 목록 |
| 7 | 미매칭 | drop (`no-keyword-match`) | 화이트리스트 방식 |
| 8 | 재기동 직후 첫 사이클 | 기록하되 발송 안 함 | 재기동 폭탄 방지 (pipeline에서 처리) |

> **중요**: `pblntf_ty`(공시유형)는 **요청 파라미터일 뿐 응답에 포함되지 않는다.** 응답 필드는 `corp_cls`, `corp_name`, `corp_code`, `stock_code`, `report_nm`, `rcept_no`, `flr_nm`, `rcept_dt`, `rm` 9개뿐이다. 유형별로 거르려면 유형마다 별도 호출이 필요해 API 예산이 배수로 늘어나므로, **모든 유형 판별은 `report_nm` 패턴으로 수행한다.**

**게이트 4 — 정정 접두어별 처리**

| 접두어 | 처리 | 근거 |
|---|---|---|
| `[기재정정]` `[첨부정정]` `[첨부추가]` | drop | 오탈자·서류 보완 |
| `[발행조건확정]` | high | 유상증자 발행가 확정 = 주가 직결 |
| `[정정명령부과]` `[정정제출요구]` | critical | 금감원 제재 = 악재 신호 |

**게이트 6 — `critical` 키워드**

```
단일판매·공급계약체결 / 무상증자결정 / 자기주식취득결정
유상증자결정 / 전환사채권발행결정 / 신주인수권부사채권발행결정
최대주주변경 / 주식분할결정 / 감자결정 / 회사합병결정
횡령·배임 / 상장폐지 / 관리종목지정 / 거래정지
부도발생 / 회생절차개시신청 / 영업정지
```

**`high` 키워드**

```
매출액또는손익구조30%(대규모법인은15%)이상변동
타법인주식및출자증권취득결정 / 영업양수도 / 현금·현물배당결정
조회공시요구(풍문또는보도)에대한답변
```

**게이트 5 — 명시적 노이즈 (drop)**

```
사업보고서 / 반기보고서 / 분기보고서        ← 정기공시
임원·주요주주특정증권등소유상황보고서        ← 최대 노이즈원 (일 수백 건)
기업설명회(IR)개최 / 정기주주총회소집공고 / 결산실적공시예고
```

**지분공시(`D`)** 는 양이 압도적이므로 기본 전량 drop하되, **5% 신규 취득**과 **경영참가 목적 변경**만 살린다.

### 7.3 2차 LLM

대상: `high`, `normal`만. 공시 본문은 목록 API가 아닌 별도 문서 API로 조회한다 (일 수십 건 수준이라 한도 영향 미미).

**수행:**
1. 본문 3줄 요약
2. 정량 추출 — 계약금액, 증자 규모, 지분율
3. 비율 계산 — 예: "계약금액 500억 = 최근 연매출의 23%"

**금지:**
- 호재/악재 판단, 목표가, 매수·매도 의견

3번은 **사실 계산**이므로 규제 대상이 아니면서 차별화를 제공한다. 이것이 규제선을 넘지 않고 가치를 만드는 지점이다.

모든 발송 하단에 `정보 제공 목적이며 투자 권유가 아닙니다` 고지를 고정한다.

### 7.4 룰 품질 관리

**비공개 채널 단계** — 운영자만 구독한 채널에 **실제로 발송하면서** 룰을 다듬는다. 섀도 모드(DB 기록만)를 쓰지 않는 이유:

1. 섀도 모드는 **발송 경로를 전혀 테스트하지 않는다.** rate limit, 마크다운 이스케이프, 메시지 길이 초과 등이 공개 전환 시점에 한꺼번에 터진다.
2. 실제 사용 맥락에서 보는 편이 피드백 루프가 빠르다.

**`drop` 다이제스트** — 발송만 보면 `pass`만 보이고 **놓친 공시는 영원히 보이지 않는다.** 초기 룰셋의 가장 흔한 실패는 과발송이 아니라 **과필터링**이다. 따라서 매일 저녁 "상장사 공시인데 키워드 미매칭으로 버려진 건"만 추려 운영자에게 발송한다 (일 20~40건 수준).

**골든 테스트셋** — 비공개 단계에서 수집한 실제 공시 100건 내외를 기대 Verdict와 함께 고정한다.

```
core/filters/__fixtures__/golden.json
```

룰 수정 시 회귀를 막는다. 필터가 순수 함수이므로 네트워크 없이 밀리초 단위로 전량 검증된다.

## 8. 발송

### 8.1 Transactional Outbox

```
BEGIN;
  INSERT INTO events (...);   -- 중복이면 충돌 → 전체 롤백
  INSERT INTO outbox (...);   -- 같은 트랜잭션
COMMIT;
```

"DB엔 있는데 발송 유실" / "발송했는데 기록 없음"이 **구조적으로 불가능**해진다. 메시지 브로커(Redis, RabbitMQ)는 도입하지 않는다 — 1인 프로젝트에 과설계다.

### 8.2 Rate limit 대응

텔레그램 봇은 같은 채팅에 **분당 약 20건**, 전체 **초당 약 30건** 제한이 있다. 장 마감 직후와 실적 시즌에 실제로 걸린다.

1. **자체 토큰 버킷** — 분당 15건으로 스스로 제한 (429를 받기 전에 조절)
2. **병합 발송** — 대기 3건 이상이면 한 메시지로 묶는다. `critical`은 묶지 않고 단독 발송
3. **429 처리** — 응답의 `retry_after` 값만큼 대기. 임의 추측 금지

### 8.3 재시도와 TTL

```
시도  1 →  2  →  3  →  4  →  5
대기  5s → 15s → 1m → 5m → 30m
```

**늦은 알림은 가치가 0이거나 해롭다** (이미 주가에 반영된 뒤 도착하면 신뢰를 깎는다). 따라서 티어별 유효기간 초과 시 발송을 포기하고 `dead` 처리한다.

| 티어 | TTL |
|---|---|
| `critical` | 5분 |
| `high` | 30분 |
| `normal` | 2시간 |

## 9. 자가치유와 운영

### 9.1 4계층

**① 프로세스** — Docker `restart: always`. 미처리 예외는 로그만 남기고 **즉시 종료**한다 (crash-only design). 예외를 삼키고 도는 프로세스는 "살아 있지만 일을 안 하는" 상태가 되어 heartbeat까지 통과해버리므로 감지 불가능하다.

**② 루프** — 폴링 실패로 프로세스를 죽이지 않는다. 연속 실패 횟수를 세어 임계 초과 시 알림.

**③ 외부 감시 (필수)** — 정상 루프마다 외부 서비스에 ping. 끊기면 외부에서 운영자에게 알린다. **VM 자체가 죽는 경우를 잡는 유일한 수단**이므로 반드시 워커 외부에 둔다.

**④ 서킷 브레이커** — DART 점검(`800`)이나 연속 실패 시 폴링 주기를 자동 확대해 API 예산을 보호한다.

### 9.2 장애 시나리오

| 장애 | 감지 | 대응 | 사람 개입 |
|---|---|---|---|
| 프로세스 크래시 | Docker | 자동 재시작 | 불필요 |
| DART 일시 오류 | 루프 카운터 | 다음 주기 재시도 | 불필요 |
| DART 점검 (`800`) | 에러코드 | 주기 확대 | 불필요 |
| 한도 초과 (`020`) | 에러코드 | 장기 백오프 + 알림 | 확인만 |
| 텔레그램 429 | 응답 | `retry_after` 대기 | 불필요 |
| 텔레그램 지속 실패 | 재시도 소진 | `dead` + 다이제스트 | 확인만 |
| DB 일시 단절 | 연결 실패 | 재시도, 큐 보존 | 불필요 |
| **VM 다운** | **외부 heartbeat** | — | **필수** |

즉시 개입이 필요한 것은 마지막 한 줄뿐이다. 이것이 "실시간 서비스"와 "실시간 대응 불가"가 양립하는 근거다.

### 9.3 일일 다이제스트

```
발송   critical 4 · high 12 · normal 8
버림   상장사인데 미매칭 27건   ← 룰 튜닝 후보
API    8,432 / 20,000 (42%)
에러   DART 타임아웃 3 · 텔레그램 429 1
dead   0
지연   중앙값 2.8초
```

**지연 측정의 한계**: "우리가 처음 본 시각 → 발송 시각"만 측정 가능하다. DART 접수 시점부터 API 노출까지의 구간은 **관측 불가능**하다. 실제 체감 지연은 이 수치보다 크므로, 대외적으로 지연을 표기할 경우 이 점을 명시해야 한다.

## 10. 테스트 전략

| 대상 | 방식 | 네트워크 |
|---|---|---|
| `core/filters` | 단위 테스트 + 골든셋 회귀 | 없음 |
| `core/policy` | 단위 테스트 | 없음 |
| `adapters/*` | 고정 fixture 기반 계약 테스트 | 없음 |
| `pipeline` | fake 어댑터 주입 통합 테스트 | 없음 |

**실제 네트워크를 호출하는 자동 테스트는 두지 않는다.** CI에서 재현 불가능하고 외부 장애로 실패한다. DART 실응답은 fixture로 고정해 사용한다.

도구: Vitest.

## 11. 인프라

| 레이어 | 선택 | 월 비용 |
|---|---|---|
| 워커 | OCI Always Free (AMD Micro 시작 → ARM 이전) + Docker | $0 |
| 계정 | **PAYG 업그레이드 필수** (한도 내 과금 0원) | $0 |
| DB | Supabase (서울 리전) | $0 |
| 외부 감시 | Healthchecks.io 류 무료 티어 | $0 |
| 발송 | 텔레그램 Bot API | $0 |
| LLM | 저가 모델, 일 50~150건 | ~$5 |

### OCI 관련 결정

- **PAYG 업그레이드는 필수다.** Always Free 계정의 유휴 인스턴스는 회수 대상인데, 저부하 폴링 워커는 정확히 그 프로필에 해당한다. PAYG로 전환하면 한도 내 사용 시 청구액 $0을 유지하면서 회수를 피한다.
- ARM(Ampere A1)은 용량 부족이 상습적이므로 **AMD Micro(1GB)로 시작**한다. Node 폴링 워커에 충분하다.
- 무료 계정 정지 사례가 보고된 바 있으므로 **OCI 전용 서비스에 의존하지 않고** Docker + 환경변수만으로 이전 가능하게 유지한다.
- 워커가 아웃바운드 전용이므로 인바운드 포트를 열 필요가 없다 (SSH 제외). OCI의 VCN/Security List/iptables 이중 방화벽 함정을 회피한다.

### 주요 라이브러리

Node.js LTS · 내장 `fetch` · `setTimeout` 루프 · Drizzle + postgres.js · zod(외부 응답 검증) · grammY · pino · Vitest

## 13. 성공 기준

- **1단계 완료**: 비공개 채널에서 7일 연속 무중단 가동 + 골든셋 100건 확보 + 과필터링 일 5건 이하
- **90일 벤치마크**: 공개 채널 구독자 **300명**. 미달 시 유통 채널(커뮤니티 시딩·검색 유입)을 먼저 재점검하고, 그래도 정체면 주제를 재검토
- 참고: 마이크로 SaaS의 82%가 월 $5K 미만, 중앙값 월 $500 수준이다. 수치는 상한이 아닌 참고치로 본다.
