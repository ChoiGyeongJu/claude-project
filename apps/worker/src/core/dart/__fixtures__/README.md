# golden.json — DART 필터 골든 회귀 세트

## 이게 뭔가

`rules.ts`(`evaluateDart`)가 실제 DART 목록 API 응답에 대해 **지금** 내리는 판정을
130건의 실측 필링에 박아 넣은 것이다. `golden.test.ts`가 이 픽스처를 로드해서
`normalizeDartItem` + `evaluateDart`에 넣고, 결과가 픽스처에 적힌 `expected`와
정확히 같은지 확인한다.

목적은 하나뿐이다: **키워드를 고치다가 기존 판정이 조용히 바뀌는 것을 막는 것.**

## 왜 이게 필요했는가

`rules.ts`는 실측 데이터로 두 번 튜닝됐다(커밋 `bdcb58e`, `904f613`, 557건 →
1,162건 통과). 그 과정에서 유닛 테스트로는 절대 잡을 수 없는 실패 모드가 하나
드러났다:

> 플래그십 키워드(횡령·배임)가 코드에서는 U+00B7(가운뎃점 `·`)로 적혀 있었는데,
> DART는 U+318D(한글 자모 아래아 `ㆍ`)를 압도적으로 더 많이 쓴다. 그래서 이
> 키워드는 실측 표본 전체에서 단 한 건도 매칭시키지 못했다 — 그런데도 기존
> 유닛 테스트는 전부 통과하고 있었다. 테스트 픽스처가 코드와 **같은** 손타이핑
> 오타(U+00B7)로 적혀 있었기 때문이다.

코드와 테스트가 서로 합의했을 뿐, 둘 다 현실(DART가 실제로 보내는 바이트)에
대해서는 틀렸다. 유닛 테스트를 아무리 늘려도 이 종류의 버그는 못 잡는다 —
코드와 테스트가 같은 손에서 같은 실수를 반복하기 때문이다. 유일한 방어는 코드가
아니라 **실제 응답 바이트**를 기준으로 판정을 고정하는 것이다. 이 픽스처가
그 기준이다.

## 왜 손으로 타이핑하는 게 금지인가

이 파일의 모든 `item` 필드(`report_nm`, `corp_cls`, `stock_code`, `corp_name`,
`rcept_no`, `rcept_dt`, `flr_nm`, `rm`)는 실제로 캐시된 DART 응답
(`filings.json`, 20영업일 · 15,477건)에서 프로그램으로 그대로 복사됐다. 사람이
한글 문자열을 다시 타이핑하는 순간 — 특히 가운뎃점처럼 시각적으로 구분이 안
되는 문자에서 — 위와 똑같은 실패 모드를 이 픽스처 안에 다시 만들어 넣을 위험이
있다. 그러면 이 파일은 "실측을 고정한 안전망"이 아니라 "또 하나의 손타이핑
합의"가 되어버려서, 존재하는 이유 자체가 사라진다.

그래서 이 픽스처는 항상 **생성**된다 — 골라 붙이지 않는다. 아래 "재생성/확장
방법"을 반드시 스크립트로 실행하고, JSON 결과물을 그대로 커밋한다. `note`
필드(사람이 읽는 설명)만은 예외다 — 이건 원본 DART 데이터가 아니라 이 픽스처를
만든 사람의 주석이므로 자유롭게 다시 쓰거나 다듬어도 된다. 절대 다시 타이핑하면
안 되는 것은 `item` 객체 안의 8개 필드뿐이다.

## 구조

```jsonc
{
  "note": "사람이 읽는 설명 — 왜 이 필링이 여기 있는지, 무엇을 핀하는지",
  "item": {
    "report_nm": "...",   // evaluateDart가 실제로 읽는 8개 필드,
    "corp_cls": "...",    // filings.json에서 그대로 복사 (corp_code는 제외 —
    "stock_code": "...",  // evaluateDart가 읽지 않는 필드라서 픽스처에 넣지
    "corp_name": "...",   // 않는다. golden.test.ts가 테스트 실행 시 더미
    "rcept_no": "...",    // corp_code를 채워 DartListItem 타입을 만족시킨다.)
    "rcept_dt": "...",
    "flr_nm": "...",
    "rm": "..."
  },
  "expected": { "action": "pass", "tier": "critical", "rule": "keyword:..." }
  // 또는       { "action": "drop", "reason": "no-keyword-match" }
}
```

## 커버리지

130건, 아래를 전부 실측 데이터로 커버한다 (`golden.test.ts`의 `EXPECTED_RULES` /
`EXPECTED_DROP_REASONS`가 이 목록을 하드코딩해서 감시한다 — 항목이 하나라도
빠지면 커버리지 테스트가 실패한다):

- **`evaluateDart`가 실측 데이터에서 실제로 내는 rule 41종 전부** (키워드 38종 +
  접두어 3종). 이 목록은 `keywords.ts`의 배열을 세어서 만든 게 아니라, filings.json
  15,477건을 전부 `evaluateDart`에 통과시켜 실제로 fire한 rule을 센 것이다 —
  그래야 "목록에는 있지만 실측 데이터에는 없는" 키워드가 숫자로 드러난다.
- **모든 tier**: critical / high / normal.
- **모든 drop reason** 6종: `no-stock-code`, `market-not-target`,
  `periodic-report`, `minor-correction`, `noise`, `no-keyword-match`.
- **가운뎃점 두 표기**: `횡령` 계열에서 U+00B7(·, 실측 2건)과 U+318D(ㆍ, 실측
  7건) 각각 하나씩. Finding 1의 그 버그.
- **거래정지 분기**: 기계적 매매정지(액면병합/전자등록 변경 → normal로 강등)
  2건, 실제 이상 신호(마커 없음 → critical 유지) 2건, 그리고 "정리매매/상장폐지
  사유는 critical 유지" 요건의 실측 사례(제목에 "상장폐지"가 있어 실제로는
  `keyword:상장폐지`로 라벨링되지만 — 배열 순서상 상장폐지가 거래정지보다 먼저
  검사되기 때문이다 — tier는 여전히 critical) 1건.
- **접두어 처리**: `[기재정정]`/`[첨부정정]`/`[첨부추가]` drop(minor-correction)
  각 1건(그중 2건은 본문에 critical 키워드가 있어도 정정 게이트가 먼저 이긴다는
  것까지 보여준다), `[정정명령부과]` critical 통과(실측 1건뿐, 이중 대괄호에서
  첫 번째만 본다는 것도 함께), `[정정제출요구]` critical 통과 3건.
- **게이트 순서 회귀 5건 전부** — 노이즈 패턴과 화이트리스트 키워드 둘 다에
  걸리는 실측 사례. 튜닝 패스에서 실제로 발견된 두 종류를 하나도 빠짐없이
  핀했다: 최대주주등소유주식변동신고서(최대주주변경시) 3건, 회사합병결정이
  섞인 임시주주총회소집결의 철회 2건.

## 커버되지 않은 것 — 지어내지 않고 있는 그대로 적는다

- **`CRITICAL_KEYWORDS`의 `주식분할결정`과 `부도발생`은 이 20영업일 표본에 단
  한 건도 없다.** `filings.json` 15,477건 전체를 grep해도 0건이다. 두 키워드
  모두 코드에는 있고 로직도 정상이지만, 이 표본 기간에는 그런 공시가 아예
  일어나지 않았다. 합성 픽스처를 만들어 채우지 않았다 — 과제 지침대로, 없는
  건 없다고 적는다. 더 긴 기간의 데이터를 다시 캐시하면 이 두 rule도 실측으로
  채울 수 있을 것이다.
- **"인식되지 않는 대괄호 접두어가 게이트 4를 통과해 게이트 3(정기보고서) 등
  후속 게이트로 흘러가는" 사례가 상장 종목(ticker+market 보유)에는 없다.**
  전체 데이터셋에서 `PREFIX_RULES`에 없는 대괄호 접두어는 `[변경등록]` 하나뿐이고
  (실측 4건), 넷 다 `corp_cls=E`이며 `stock_code`가 비어 있다 — 즉 게이트
  4(정정 접두어)에 닿기도 전에 게이트 1(비상장 제외)에서 이미 drop된다. 이
  드롭 자체는 픽스처에 `drop:no-stock-code` 사례로 포함해 뒀지만(주석에 이
  사정을 그대로 적어 뒀다), "미인식 접두어가 실제로 후속 게이트 로직을 타는"
  경로는 이 표본으로는 실측할 수 없었다. `rules.test.ts`의 손타이핑 픽스처
  (`[변경]사업보고서`)가 이 분기의 유일한 커버리지이며, 이 골든 세트의 범위 밖이다.
- **정기보고서 하위 3종 중 `분기보고서`는 상장 종목 기준 실측 0건이다**
  (사업보고서 12건 + 반기보고서 28건 = periodic-report 40건 전부). 20영업일
  창이 마침 분기보고서 제출 시즌과 겹치지 않았을 뿐, `periodic-report`
  drop reason 자체는 두 실제 하위 유형으로 이미 커버된다.

## 재생성/확장 방법

키워드를 고치고 나서 "이 판정이 왜 바뀌었는지" 확인하고 싶거나, 새 필링
캐시로 커버리지를 넓히고 싶을 때:

1. DART 목록 API 응답을 캐시해서 `filings.json` 같은 배열 파일을 만든다
   (형식은 `schema.ts`의 `dartListItemSchema` — `corp_cls`, `corp_name`,
   `corp_code`, `stock_code`, `report_nm`, `rcept_no`, `flr_nm`, `rcept_dt`,
   `rm` 문자열 필드 전부).
2. 그 파일을 읽어 배열의 각 항목을 `normalizeDartItem` → `evaluateDart`에
   통과시키는 **임시 vitest 테스트 파일**을 `src/core/dart/` 아래 작성한다
   (예: `_scratch.generate.test.ts` — 파일 이름 앞에 언더스코어를 붙이면 실수로
   커밋에 남았을 때 눈에 띈다. 커밋하기 전에 지운다). core는 순수해야 하고
   `.ts`를 직접 실행하지 않으므로, 실행은 항상 `pnpm --filter @app/worker test --
   <파일 패턴>`으로 vitest를 통해서만 한다 — `node`나 `tsx`로 직접 돌리지 않는다.
3. 그 스크립트 안에서 (a) 판정을 `pass:tier:rule` / `drop:reason` 키로 버킷팅해서
   지금 무엇이 fire하는지 실측으로 다시 세고, (b) 새로 커버하고 싶은 버킷에서
   항목을 골라 `{ note, item, expected }` 형태로 `golden.json`에 **덮어쓴다**
   (`JSON.stringify`로 — `expected`는 반드시 그 스크립트 안에서 실제
   `evaluateDart` 호출 결과를 그대로 쓴다. 사람이 손으로 tier/rule/reason을
   적지 않는다).
4. `pnpm --filter @app/worker test`로 `golden.test.ts`가 전부 통과하는지,
   커버리지 테스트(rule 41종 + drop reason 6종)가 여전히 통과하는지 확인한다.
   새 rule이 fire하기 시작했다면(키워드를 추가한 경우) `golden.test.ts`의
   `EXPECTED_RULES`에도 그 rule 문자열을 추가한다 — 안 그러면 새 rule은
   "추가됐지만 아무도 핀하지 않은" 상태로 조용히 커버리지 밖에 남는다.
5. 임시 생성 스크립트를 지운다. 커밋에는 `golden.json`, `golden.test.ts`,
   이 README만 남긴다.

## 이 픽스처가 보장하지 않는 것

- 새로 추가한 키워드가 "옳다"는 것 — 그건 실측 카운트로 사람이 판단할 일이다.
  이 픽스처는 오직 "기존에 이미 옳다고 확인한 판정이 그대로 유지되는가"만 본다.
- 미래에 DART가 새로운 표기 변형을 들고 나올 가능성 — `canonicalizeTitle`의
  방어 대상 문자 집합(`MIDDLE_DOTS`)에 없는 문자가 나오면 이 픽스처는 아무
  경고도 못 한다. 그건 이 픽스처가 아니라 다음 실측 튜닝 패스의 몫이다.
